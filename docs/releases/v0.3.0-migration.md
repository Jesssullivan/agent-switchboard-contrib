# v0.3.0 migration: security bundle and CLI ergonomics

Ruling: R-C944 (TIN-5770 comment `23fdf965`, operator interview
2026-10-19). Ticket: TIN-4655.

v0.3.0 is one coordinated breaking release. A v0.2 client talking to a
v0.3.0 broker fails loudly: it gets HTTP 405, 400 or 415 with a typed JSON
error. It never gets a silent fallback. Upgrade the broker and every client
(`swb` hooks, `swb channel`, MCP harness configuration, lab's pinned
package) together.

This note is for hook and client authors. The workspace version is 0.3.0.
Released as v0.3.0 (SWB-R62, 2026-10-23); the approved image digest is in
[approved-broker.json](approved-broker.json).

## What changed on the wire

| Area | v0.2.x | v0.3.0 |
|---|---|---|
| `register` | `{agent_id, lease_seconds}` | `{agent_id, lease_seconds, end_token}` |
| `end` (REST and MCP) | `{me, proc_start}` | `{me, end_token}`. A body with `proc_start` and no `end_token` gets 400 with a message that names `end_token`. |
| `peers` listing | every row, every state, unbounded, with `proc_start` | live rows only by default, one row per (harness, host, session id), paginated, no `proc_start` |
| Lease refresh | `GET /v1/peers?me=` | `POST /v1/peers {"me": ...}`. `GET /v1/peers?me=` answers 405. |
| Inbox | `GET /v1/inbox?me=&limit=&wait_seconds=` | `POST /v1/inbox {"me", "limit", "wait_seconds"}`. `GET /v1/inbox` answers 405. |
| Errors | `{"error": "..."}`, HTTP 400 for nearly everything | `{"error": "...", "code": "..."}` with a status per kind (table below) |
| Health | none | `GET /healthz` on the main listener (Host-guarded) and on the metrics listener (unguarded, for probes) |
| MCP | 5 tools, no field descriptions | 6 tools (`end` added), every input field described |
| Retention | pruned inside every `send` and every 250 ms inbox long-poll tick | pruned at startup and on the broker's interval (1 h) |

### End token

- `register` returns `end_token`: 64 lowercase hex characters (an
  HMAC-SHA256 that the broker derives from a per-row nonce). The broker
  stores the nonce and its key. It does not store the token.
- Every `register` mints a new token and every earlier token stops
  working, even when `proc_start` is unchanged. Knowing a row's
  `proc_start` therefore never retrieves the token its registrant holds. A
  hook that registers on every prompt saves the newest token each time.
  Two registrations of one agent id that race can leave a client holding
  the older token; its `end` then answers `unknown` and the session decays
  instead.
- `end` with any other token returns `{"state":"unknown"}` and ends
  nothing. The answer does not say whether the session exists.
- Treat the token as a secret. Never print it, log it or pass it on a
  command line. The audit line never carries it.
- Identity is still self-asserted (ADR-0001), so the token is **not**
  takeover-proof. Anyone who can register can re-register any agent id,
  receive a fresh token and end that session. What the token does prevent
  is ending a session without registering: v0.2 allowed that because
  `peers` handed out the `proc_start` that `end` checked. It does not
  authenticate who registered.
- Over MCP, the `register` result carries `end_token`, so the token enters
  the calling model's context and transcript. This is a known exposure,
  kept because the MCP `end` tool needs the token. An adapter that ends
  sessions itself (lab's Pi adapter, below) should keep the token and strip
  it before the model sees the result. The REST clients in `swb` never
  print it.
- Rows registered under v0.2 have no nonce. Nothing can end them. They
  decay from live to idle to gone, and the next register gives them a
  token.

### `peers`

- `POST /v1/peers` takes `{"me"?, "all"?, "host"?, "limit"?, "cursor"?,
  "proc_start"?}`. `proc_start` keeps only rows whose latest registration
  used it; the caller supplies its own, and rows never show it.
  `GET /v1/peers` takes `all`, `host`, `limit` and `cursor` as a query
  string (`all=1|true|0|false`). An unknown query parameter is a 400.
- Without `all`, only live rows are listed (refreshed within 900 s).
  `all: true` adds idle, gone and ended rows.
- One row per (harness, host, session id): when two agent ids share all
  three (for example a resumed session in a new process), only the most
  recent registration is listed. The other row still exists and can still
  send, receive and refresh its lease. Sessions with a fixed label on
  different hosts or harnesses (lab's IDE channels register as `junie` or
  `ai-assistant`) stay separate rows.
- Pages hold `limit` rows (default 50, at most 200), ordered by `agent_id`.
  The response is `{"peers": [...], "next_cursor": <agent_id>|null}`. Pass
  `next_cursor` back as `cursor` to get the next page.
- A row is `{agent_id, harness, host, last_seen, state}`. `proc_start` is
  gone.

### Errors

Every error body is `{"error": <short message>, "code": <code>}`.

| `code` | HTTP | When |
|---|---|---|
| `invalid_argument` | 400 | A field is missing, mistyped or invalid |
| `invalid_json` | 400 | The body is not JSON, or not a JSON object |
| `unsupported_media_type` | 415 | A POST without `Content-Type: application/json` |
| `unregistered` | 404 | `peers` with a `me` that names no session |
| `message_unavailable` | 404 | `ack` of a message that is not yours, or has expired |
| `not_found` | 404 | No such route |
| `method_not_allowed` | 405 | A removed GET route (with `Allow: POST`), or a wrong method |
| `msg_id_conflict` | 409 | A `msg_id` reused with a different sender or body (SWB-R46) |
| `internal` | 500 | The store failed |

The Host/Origin guard's 403 bodies (`missing host`, `host not allowed`,
`origin not allowed`) are unchanged. MCP tool errors carry the same JSON
object as their text content.

### Why POST

A browser sends no `Origin` on a simple cross-site GET, so in v0.2 a page
that knew an agent id could refresh its lease or count a delivery through
`GET /v1/peers?me=` and `GET /v1/inbox?me=` (ADR-0001, "Known residual,
cross-site GET"). Since v0.3.0 every call that changes state is a POST with
a JSON body. A browser cannot send that body cross-site without a CORS
preflight, and the Origin guard refuses the request either way. A caller's
own id (`me`) also no longer travels in a URL that proxies and access logs
record. Another agent's id still can: a passive `GET /v1/peers?cursor=`
carries one, and `swb peers --cursor` uses that form.

## The `swb` CLI

- `swb --help`, `swb -h`, `swb help` and `swb <verb> --help` print usage
  on stdout and exit 0. `swb --version`, `swb -V` and `swb version` exit 0.
  An unknown verb still exits 2, with the usage on stderr.
- `swb whoami` no longer registers. It prints
  `{"agent_id": ..., "registered": false}` from the `SWB_*` environment and
  makes no broker call. `swb whoami --register` registers the session,
  saves the end token, and prints the response with the token replaced by
  `end_token_file`.
- Hooks (`swb hook <harness> <event>`) save the end token on every
  successful register. SessionEnd ends the session with the saved token and
  deletes the file. Without a saved token SessionEnd makes no broker call.
- The token file is `$SWB_STATE_DIR/sessions/<agent_id>.token`.
  `SWB_STATE_DIR` defaults to `$XDG_STATE_HOME/swb`, then
  `$HOME/.local/state/swb`. Only absolute paths count. The directory is
  0700 and the file is 0600. Each save also removes token files in that
  directory not rewritten for 7 days, which is what a session that crashed
  without SessionEnd leaves behind.
- `swb peers [--all] [--host HOST] [--limit N] [--cursor AGENT_ID]`.
- `swb inbox`, the UserPromptSubmit notice and `swb channel` read the inbox
  with `POST /v1/inbox`.
- `swb channel` finds its own row with `POST /v1/peers {"all": true,
  "host": <SWB_HOST>, "proc_start": <SWB_PROC_START>}` (up to 5 pages),
  then matches host, pid and, when set, harness. The `proc_start` filter
  keeps the v0.2 guard against a crashed session that reused the pid.
  `swb channel` now needs `SWB_PROC_START` for that lookup.
- `swb <verb> --help` counts only when `--help` (or `-h`) directly follows
  the verb, so `--ruling -h` is a flag value.
- `swb doctor --register` also refreshes the saved end token.

## Needed lab change (later act)

Lab pins the `swb` package. Nothing in this release changes lab. Before lab
moves its pin to v0.3.0:

1. `nix/home-manager/jetbrains-config.nix` (`tinyland-ide-swb-channel`)
   registers the IDE session with `swb whoami`. Change that line to
   `swb whoami --register`, or the IDE session is never registered and
   peers cannot find it. The wrapper already discards the output and is
   bounded by `timeout 5`, and v0.3.0 never prints the token.
2. `nix/home-manager/claude-code.nix` (the `switchboardHook` wrapper around
   `swb hook claude <event>`, the SessionStart, UserPromptSubmit, Stop and
   SessionEnd bindings) and the Codex binding in
   `nix/home-manager/codex.nix` (`swb hook codex <event>` for SessionStart
   and UserPromptSubmit) need no change. The hook saves and spends the end
   token itself. The hook process must see `HOME` (or `XDG_STATE_HOME` or
   `SWB_STATE_DIR`), which a Claude Code or Codex hook does.
3. The SessionEnd binding only works for sessions whose SessionStart ran
   under v0.3.0: an older session has no token file, so it decays instead
   of ending.
4. Lab's Pi runtime (`config/agent-harness/pi-runtime/`):
   - `swb-session.ts` ends the session with
     `POST /v1/end {"me", "proc_start"}`, which v0.3.0 refuses with 400.
     It should keep `end_token` from its own `POST /v1/register` response,
     in memory only, and send `{"me", "end_token"}` at `session_shutdown`.
     Its test fixtures (`swb-session-test.ts`,
     `pi-agents-mcp-adapter-test.ts`,
     `nix/tests/fixtures/pi-agents-loader-integration-test.ts`) answer
     `/v1/register` without a token and need one.
   - `pi-agents-mcp-adapter.ts` returns the MCP `register` result to the
     model as text. That result now carries `end_token`, so the adapter
     should drop that field before returning it. Its five-tool allowlist
     already filters out the new `end` tool, and its register-schema check
     still holds: the required fields and their types did not change.
   - `pi-agents-observation-test.ts` carries a register-schema fixture;
     update it to the v0.3.0 `tools/list` (the `register` description and
     the `proc_start` description changed; required fields did not).
   - Any other script that reads `GET /v1/inbox` or `GET /v1/peers?me=`
     needs the POST form.
5. `nix/home-manager/assets/skills/peer-dialog/SKILL.md` says
   `swb whoami` registers. Change it to `swb whoami --register`.
6. Any probe that used `GET /v1/peers` as a liveness check can use
   `GET /healthz` instead. On the metrics listener it needs no Host
   allowlist entry.

## Upgrade order

1. Deploy the v0.3.0 broker. The store migrates in place: it adds
   `session_id`, `registered_seq` and `token_nonce` to `sessions`, and
   fills `session_id` from each agent id. Old rows stay listed until they
   decay.
2. Move every client to v0.3.0 in the same window. A v0.2 hook against a
   v0.3.0 broker still registers. Its inbox read and its SessionEnd fail
   with typed errors, and hooks stay exit-0 (SWB-R10).
